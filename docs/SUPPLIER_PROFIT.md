# Supplier ба нэгдсэн Profit: жижиг finite-scenario жишээнүүд

Эдгээр нь одоогийн v0.5.0 `indexed_program` + HiGHS MILP ашигладаг.
Математик core-д domain-specific solver, шинэ API эсвэл шинэ function нэмээгүй.
Бүх параметр зохиомол; Oracle/ERP өгөгдөл болон хуучин төсөлд өөрчлөлт хийхгүй.

## 9. Supplier optimization

Файл: `examples/indexed_supplier.json`.
Нэг SKU, хоёр нийлүүлэгч, захиалга өгөх t=0 ба хүлээн авах t=1,
хоёр scenario (тус бүр 0.5). Lead time=1; өмнөх pipeline=0.

| Параметр | Нийлүүлэгч 0 | Нийлүүлэгч 1 |
|---|---:|---:|
| Нэгжийн өртөг | 1 | 3 |
| Захиалга нээх өртөг | 1 | 1 |
| MOQ | 2 | 2 |
| Capacity | 6 | 6 |
| Scenario 0-д ирэх хувь | 1 | 1 |
| Scenario 1-д ирэх хувь | 0.5 | 1 |

Нийт худалдан авалтын төлөвлөгөө t=0-д 6, t=1-д 0. Эдгээр нь шинэ давхар
захиалга биш: `SUM_OVER(s, order[s,t]) == purchase[t]` тэнцлээр өгсөн нийт
захиалгыг нийлүүлэгчдэд хуваана. Эрэлт t=0-д 0; t=1-д scenario 0:5, 1:6.
Дутагдлын нэгж өртөг 4. Бүх order/opened шийдвэр scenario-оос хамаарахгүй.

Бодит ирэлт = reliability[s,w] * order[s,t-1]. Дутагдалд bounded
`positive_part` ашиглана. Найдвартай байдал нь энд зөвхөн нийлүүлэлтийн хувь;
санамсаргүй lead time, бүх нийлүүлэгчийн бүх SKU-ийн бодит статистикийг
энэ жишээ загварчлаагүй.

### Үйлчилгээний магадлалын нөхцөл

Scenario бүрийн `violation[t,w]` binary хувьсагчтай:

```
demand[t,w] - SUM_OVER(s, reliability[s,w]*order[s,t-lead])
    <= big_m * violation[t,w]
SUM_OVER(w, prob[w]*violation[t,w]) <= epsilon
```

big_m=6 нь энэ өгөгдлийн demand<=6, arrival>=0 гэдгээс авсан зөв дээд
хязгаар. Өгөгдөл өөрчлөгдвөл хязгаарыг дахин тооцно. violation=1 нь зөрчил
зөвшөөрсөн төлөв; заавал бодит дутагдалтай гэсэн хоёр талт тодорхойлолт биш.
Нөхцөл нь нийлүүлэгч тус бүрт биш, нийт ирэлтэд үйлчилнэ.

| epsilon | Нийлүүлэгч 0-ийн Q | Нийлүүлэгч 1-ийн Q | Нийт өртөг |
|---|---:|---:|---:|
| 0.5 | 6 | 0 | 13 |
| 0 | 0 | 6 | 19 |

Эхний хувилбар: худалдан авалт 6 + setup 1 + хүлээгдэж буй дутагдлын
өртөг 0.5×3×4=6. Хоёр дахь нь хоёр scenario-д хоёуланд дутагдалгүй.
Магадлалын баталгаа нь зөвхөн өгсөн finite scenario measure-д хамаарна.

## 10. Нэгдсэн Profit optimization

Файл: `examples/indexed_profit.json`.
Энэ бол 10-р зураг дахь бүх retail сүлжээний бүрэн хэрэгжилт биш.
Нэг SKU × нэг салбар × хоёр нийлүүлэгч × хоёр өдөр × хоёр scenario-ийн
хязгаарлагдсан нэгдсэн жишээ. Дөрвөн axis: supplier s, time t, scenario w,
price choice k. SKU/branch нь нэг тул тусдаа axis биш.

Захиалга, нийлүүлэгч, нийлүүлэх хэмжээ, үнэ, SKU сонголт, нэг тавиурын
шийдвэрийг нэг MILP-д **хамтад нь** оновчилно. Нийт худалдан авалт нь
SUM(order); гаднаас дахин нэмэх тусдаа replenishment order байхгүй.

- Эхний агуулахын нөөц 1, салбарын нөөц 0; өмнөх pipeline 0.
- Нийлүүлэгчийн unit/setup/reliability нь дээрхтэй ижил; capacity тус бүр 4.
- t=0-д захиалж, t=1-д ирнэ; t=0-д хуваарилалт/борлуулалт 0.
- t=1-д үнэ 6 эсвэл 9. Scenario 0-ийн эрэлт [5,3], scenario 1-ийнх [7,5].
- Хадгалалтын зардал 0.2; хуваарилалтын нэгж зардал 0.1; SKU байрлуулах
  нэг удаагийн зардал 1. Facings=selected буюу 0/1 тавиурын жижиг хувилбар.
- Захиалга, хуваарилалт, SKU/facing, үнэ нь бүгд scenario-оос үл хамаарах
  урьдчилсан шийдвэр. Борлуулалт нь t=1-ийн эрэлт ил болсны дараах шийдвэр.
- Shared хуваарилалт нь хоёр scenario-д хоёуланд нь агуулахын ирэлтэд
  багтах ёстой. Дараагийн мэдээлэлд тулгуурлан дахин хуваарилах recourse
  энэ жишээнд байхгүй; ийм бодлого илүү сайн үр дүн өгөх боломжтой.

Нөөцийн баланс болон борлуулалтын өмнөх нөөц B-г тусад нь байгуулсан:

```
W[t,w] = W[t-1,w] + SUM(arrival[s,t,w]) - allocation[t]
B[t,w] = stock[t-1,w] + allocation[t]
stock[t,w] = B[t,w] - SUM(sales[t,k,w])
available[t,w] <= B[t,w] <= stock_cap * available[t,w]
```

B нь integer учраас дээрх холбоос available=1 iff B>=1 утгыг өгнө.
`selected=0 => sales=0` нөхцөл болон сонгоогүй үнээр sales=0 нөхцөл бий.
Үнэ × борлуулалтыг үнэ тус бүрийн sales хувьсагч ашиглан яг шугамчилсан.
Борлуулалтын орлогоос худалдан авалт, setup, хадгалалт, хуваарилалт,
байршуулалтын өртгийг тус бүр нэг удаа хасна. Тусдаа service penalty=0;
борлуулалтын алдагдлыг shortage penalty гэж дахин хасаагүй.

### Шийдэл

| Гаралт | Утга |
|---|---|
| t=0 захиалга | Q0=4, Q1=2 |
| t=1 хуваарилалт | 5 |
| SKU / facing | 1 / 1 |
| Сонгосон үнэ | 9 |
| Scenario 0/1 борлуулалт | 3 / 5 |
| Эцсийн салбарын нөөц | 2 / 0 |
| Эцсийн агуулахын нөөц | 2 / 0 |
| Хүлээгдэж буй ашиг | **22.3** |

Ашиг = орлого 36 − худалдан авалт 10 − setup 2 − хадгалалт 0.2 −
хуваарилалт 0.5 − байршуулалт 1. SKU байрлуулах өртгийг 100 болговол
selected=0, борлуулалт=0, шинэ захиалга=0 болдог шалгалттай.

### Баталгаажаагүй / хамрагдаагүй хүрээ

- Олон SKU/салбар, салбар хоорондын шилжүүлэг, тээврийн нэгдсэн capacity.
- Cross-SKU substitution, log facing response, available-аас бусад SKU-ийн
  эрэлт өөрчлөгдөх D(p,f,y,o) бүрэн холбоос. Энд demand хүснэгт нь price ба
  scenario-оос хамаарна; selected/available нь борлуулалтыг зөвшөөрөх gate.
- Олон өдрийн markdown хуваарь, тасралтгүй үнийн nonlinear optimization.
- Нөөцийн аудитын G gate, бодит өгөгдлийн баталгаажуулалт, ERP action.
- Том scenario tree, sparse matrix, decomposition. Одоогийн 4 axis,
  1000 variable болон бусад solver/AST хамгаалалтын хязгаар хэвээр.

Эдгээр нь дараагийн нийтлэг чадамжийн ажлууд; энэ жишээгээр бүрэн
хэрэгжсэн гэж үзэхгүй. Томруулахдаа эхлээд олон индекс ба sparse matrix,
дараа нь мэдээллийн үе шаттай нэгдсэн загварын verification хийх хэрэгтэй.

## Ажиллуулах ба шалгах

```powershell
.\.venv\Scripts\python.exe -m math_engine examples/indexed_supplier.json
.\.venv\Scripts\python.exe -m math_engine examples/indexed_profit.json
.\.venv\Scripts\python.exe -m pytest -q tests/test_supplier_profit.py
```

Сервисүүд асаалттай үед `scripts/demo_job.py indexed_supplier --persist`,
`indexed_profit --persist` ашиглана. Persistence нь зөвхөн үйлчилгээний artifact;
Oracle руу бичихгүй. Solution нь job result-д хадгалагдана.

Тестүүд MILP-ээс тусдаа бүх боломжит integer захиалга, allocation, price,
selection-ийг тоочиж зорилгын утгыг тулгана. epsilon=0/.49/.5/1, нөөцгүй,
SKU сонгохгүй хувилбар, өртгийн давхардал, нөөц/олдоцын холбоосыг шалгана.
HTTP интеграцийн тест хоёр жишээг job/worker/compute/persistence-ээр явуулна.
